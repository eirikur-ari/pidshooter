## 1. Architecture conformance — both models agree, clean, with one shared caveat

Both reviews independently concluded `tcellui.UI` is a correct "dumb adapter": its only non-stdlib imports are `github.com/gdamore/tcell/v2`, `application/contract/outbound`, and `internal/util` (for `FormatBytes`); no reverse imports into `core/*` or other `application/*` packages exist (`grep -r "tcell" internal/core` is empty); no `tcell.Style`/`tcell.Event*`/`tcell.Button1` type ever appears above this file — the `outbound.InputEvent` family (`QuitEvent`/`ConfirmEvent`/`SpeedEvent`/`ClickEvent`) is genuinely intent-level, confirming the `MEMORY.md` note that the input-port redesign is complete; and `translateEvent` performs pure physical-input → intent translation with zero game-logic decisions (whether a click *kills* is entirely `core/game`'s call).

**The one caveat both reviews converged on, independently and from different angles:** the port is silent about terminal chrome. `outbound.TargetViewState.X/Y` is documented as sharing `Renderer.Size`'s full coordinate space, but this adapter unconditionally claims row `h-1` for the status bar and row `0` for the HUD — and only the bottom claim has a matching reservation on the domain side (`core/movement.bounceBottom`'s `height-2`). This is not an import-graph violation; it's a contract gap in the port itself, and it's the direct root cause of Finding 1 below.

**Verdict: no hexagonal-boundary violations, no changes needed on the layering axis.** Everything below is correctness, terminal-rendering fidelity, concurrency/lifecycle robustness, and test-design quality.

## 2. Test design quality — both models independently measured the same coverage numbers and found the same defect in the same test

23 tests in `tcellui_test.go`, competently organized (shared `newUI`/`nextEvent`/`rowContent` helpers, a bounded `500ms` timeout on event reads rather than an open-ended channel read — exactly the discipline `MEMORY.md`'s "Feedback: Avoid Flaky Tests" asks for). Both reviews ran `go tool cover -func` independently and got identical numbers:

```
NewUI          100.0%   Render         100.0%   drawStatusBar  100.0%
Init            85.7%   Events         100.0%   poll            78.9%
Cleanup        100.0%   drawHUD         95.0%   translateEvent 100.0%
Size             0.0%
total:          92.2%
```

Uncovered: `Init`'s `screen.Init()`-error branch, `Size()` entirely (despite being queried up to 3×/frame at 20fps by `application/game.Service`), `drawHUD`'s `scoreX < 0` narrow-terminal clamp, and `poll`'s `EventResize`/`default` branches.

**Both reviews, independently, found the same real defect in the same regression test.** `TestPollGoroutineExitsAfterCleanup` (the regression test for `docs/code-review.md` #6, "poll goroutine blocks on channel send after game exits") injects 15 × `tcell.KeyRune 'a'`. `'a'` is not in `translateEvent`'s table, so every injection is dropped before it reaches `a.ch` — the buffer never fills, `poll()` never reaches the guarded send, and the test's actual exit path is `PollEvent() == nil` after `Fini()`, not the `<-a.done` branch #6's fix added. Both reviews confirmed this via coverage (`tcellui.go:183`'s `case <-a.done:` line shows `0` hits across repeated runs) and confirmed that swapping the injected rune for a recognized one (e.g. `'+'`) flips the coverage and exercises the real path. **The fix is correct; the test that's supposed to prove it isn't testing what it claims to** — independent convergence on the exact same one-token repair (`'a'` → any translatable rune) is a strong signal this is real, not an artifact of either review's framing.

One review additionally noted `tcell.SimulationScreen`'s own semantics diverge from the real screen exactly where a lifecycle bug hides (see Finding 4) — the test suite is structurally unable to observe that class of bug no matter how much more of it were written, the same shape of gap `docs/osprocess-findings.md` found between `List()`'s and `LookupName()`'s `ps` invocations.

**Minor, independently noted:** test helpers (`newUI`, `nextEvent`, `rowContent`) are declared above the `Test*` functions that use them, the inverse of this project's stated convention (`MEMORY.md`: "Feedback: Test File Organization").

## 3. Moderate findings

### Finding 1: A target parked on row 0 is invisible under the HUD — and, the two reviews initially disagreed about this, remains fully live and killable

**Status: Fixed (2026-09-12).** Took the root-cause fix: `core/movement.bounceTop` now reserves row 0 for the HUD (`pos.Y = 1` instead of `0`), symmetric with `bounceBottom`'s existing `height-2` reservation for the status bar — this stays entirely inside `core/movement`, per the existing project precedent that row-reservation arithmetic belongs in the physics package, not at call sites (a prior attempt to move the `-2` subtraction out into callers was rejected). `bounceBottom`'s own floor was also raised from `0` to `1` so the two clamps can't fight each other and undo the new reservation on a degenerate (≤2-row) terminal. Two defense-in-depth layers were added in `tcellui.go` on top of the domain fix: `Render`'s target-draw loop now clips `tv.Y > 0` symmetrically with the existing `tv.Y < h-1`, and `poll` now drops any `ClickEvent` on row `0` or row `h-1` before it ever reaches the game, since neither row can legitimately contain a target regardless of what the domain does. Regression tests: `TestBoundsBounceTop` (updated), `TestBoundsBounceBottomDoesNotUndoTopReservation`, `TestRenderClipsTargetAtHUDRow`, `TestPollDropsClickOnHUDRow`, `TestPollDropsClickOnStatusBarRow`. The draw-order-swap half of the originally suggested fix was not needed once reachability was closed at the root — see below for what was evaluated and why.

**Evidence:** `Render` (`tcellui.go:60-84`) draws targets first, then unconditionally overwrites row `0` via `drawHUD` and row `h-1` via `drawStatusBar`. The target-draw loop only clips the *bottom*: `tv.Y < h-1` (`:74`); nothing clips `tv.Y == 0`. On the domain side the reservation is one-sided too — `core/movement.bounceBottom` clamps to `height-2` ("reserve bottom row for status bar"), but `bounceTop` clamps to exactly `0` with no analogous top reservation.

**Reproduced:** 200/200 simulated targets (`movement.NewBounds(80,25)`, 2000 ticks each) reached rendered row 0, at a mean of 56 ticks (~2.8s at the game's 20fps `frameDuration`) — this is routine physics on essentially every session, not an edge case. Rendering a target at `{X:2, Y:0}` alongside a populated HUD produces a row-0 string with the target's tag either fully erased (when it lands under HUD text) or garbled into the HUD's own text (when it lands in a gap between HUD elements) — confirmed both ways.

**The consequence — this is where the two independent reviews disagreed, and it matters:** one review characterized this as cosmetic-only, reasoning that "hit-detection reads game state, not the rendered buffer, so clickability/scoring are unaffected." The other traced the full click path and concluded the invisible target remains fully live and killable by clicking on the HUD text covering it. **I independently verified this myself** by reading `core/game/input.go:45-54` (`OnClickAt` → `roster.hitAt(x,y)`), `core/game/roster.go:49-53` (`hitAt` iterates every target and checks `isHitAt`, with zero chrome-row filtering), and `core/game/target.go:96-104` (`isHitAt` checks only `State == Alive` and the tag's rectangle — `y == int(t.Position.Y)`, no exclusion for `y == 0`). **The second review is correct, and the first review's own evidence actually supports it** — "hit-detection reads game state, not the rendered buffer" is true, but the game state it reads (an `Alive` target sitting at `Y=0`) is exactly what gets hit-tested regardless of whether anything visible is there. So: within the first few seconds of ordinary, unmodified play, in default (non-confirm) mode, a click anywhere on the visible `FREED:`/`Highscore:`/`KILLS:` HUD text can `SIGKILL` a real OS process the player never saw, with no tag drawn and no indication anything was there.

**Severity: Moderate,** and arguably the most consequential finding in this document — it's the only one where a pure rendering defect causes an unintended, irreversible `SIGKILL`. It's not Critical only because the affected process is always one the player already deliberately scoped in via their pattern, and `--confirm` mode fully mitigates it (the confirmation prompt names the PID/process before the kill lands, giving the player a chance to decline even for a target they never saw appear).

**Related, already-tracked, now quantified:** independently of chrome, `docs/code-review.md` #34 ("clicks on a visible target miss ~50% of the time") was quantified this pass: the renderer's converter rounds target position (`application/game/converter.go`, `math.Round`) while `core/game.Target.isHitAt` truncates (`int(t.Position.Y)`/`int(t.Position.X)`) — a 50-target/200-tick simulation measured the rendered cell disagreeing with the hit-tested cell on 49.6% of frames (X axis), 49.1% (Y axis), 74.1% (either axis). This is a `core`/`application` bug, not a `tcellui` one, but `tcellui` is the sole consumer of the rounded value and the acceptance criterion for whichever side gets fixed — noted here for completeness since it compounds Finding 1's user experience (misses near a target already feel arbitrary; a full miss due to invisibility is the extreme case of the same trust problem).

**Suggested fix, in order of scope, and what was actually done:** (1) minimal, `tcellui`-local: swap the draw order so chrome is drawn *before* targets, and clip `tv.Y > 0` symmetrically with the existing `tv.Y < h-1` — the clip was taken; the draw-order swap was evaluated and **not** taken, since it only changes what happens when a target *is* at row 0 (drawn on top of the HUD text vs. under it), and the actual fix closes that case at the domain level instead, matching how the bottom row is already handled (excluded outright, not merely drawn on top of chrome). (2) the "real" fix for #38's underlying coupling — a `Renderer.PlayArea()` port method, or having the application layer subtract chrome once and pass explicit bounds down to `core/movement` — was considered and **rejected**: this project already tried moving row-reservation arithmetic out of `core/movement` and into callers once before and rolled it back, on the grounds that callers (game-loop/application code) shouldn't carry UI/layout knowledge and that the physics package should stay the single source of truth for it. The fix taken instead keeps the new top-row reservation entirely inside `core/movement.bounceTop`, mirroring `bounceBottom`'s existing in-package pattern rather than reopening that settled question. (3) `poll` refusing to forward a chrome-row `ClickEvent` — taken, as defense in depth alongside the domain fix rather than instead of it.

### Finding 2: `drawStatusBar` (and latently, `drawHUD`) still use the UTF-8 byte offset as the screen column — the exact bug class `docs/code-review.md` #13 fixed in the target loop was left in three other loops

**Status: Fixed (2026-09-12).** Took the suggested fix: `drawStatusBar` and `drawHUD`'s three hand-rolled `for i, ch := range str { if i < w {...} }` loops were replaced with `tcell.Screen.PutStrStyled`, which walks by grapheme cluster and clips to the real screen dimensions internally — this closes the byte-offset bug at its root rather than patching each loop's index arithmetic. `drawHUD`'s centering math (`hiX`/`scoreX`) was also switched from `len()` (bytes) to `utf8.RuneCountInString` so the function is internally consistent, even though no currently-reachable HUD input is non-ASCII. Since `PutStrStyled` also advances by true display width rather than by rune count, this incidentally closes Finding 3's wide-rune column bug for these same three loops too — Finding 3 itself (the target-draw loop, plus the domain-side `core/game` width measurement) is unchanged by this fix and remains open. Regression test: `TestDrawStatusBarConfirmingMultiByteName`, verified against the pre-fix code to actually reproduce the byte-offset gap (`"café -server"`) before confirming it passes against the fix.

**Evidence:** `tcellui.go:148-152`:
```go
for i, ch := range statusStr {
    if i < w {
        a.screen.SetContent(i, h-1, ch, nil, statusStyle)
    }
}
```
`i` from `range` over a `string` is a byte index, not a column. #13's own fix added an independent `col` counter to the *target* loop (`:72-78`) for exactly this reason and locked it in with `TestRenderMultiByteLabelColumnLayout` — but `drawStatusBar` and all three `drawHUD` loops (`:94`, `:112`, `:119`) were never converted, and `drawHUD`'s centering math (`hiX := (w - len(hiStr)) / 2`, `:103`) additionally uses `len()` (bytes) rather than a rune/display count.

**Reachability:** `statusStr` only contains non-ASCII when the confirm-mode prompt includes a non-ASCII process name (`status.Confirming.Name`, sourced from `ps`'s `comm`/`ucomm` column, which can legitimately contain any UTF-8 byte a filename can). One extra UTF-8 byte in the name shifts every character after it one column to the right and leaks a spurious blank column at the point of divergence; combined with Finding 3's wide-rune bug, a CJK process name garbles the confirm prompt further, character-by-character. `drawHUD`'s equivalent bug is currently unreachable in practice (its inputs — `util.FormatBytes`, `%d`) are ASCII by construction, but it's the same defect, latent rather than absent.

**Severity: Moderate.** Narrower reach than Finding 1 (requires `--confirm` and a non-ASCII target name), but it's the same bug class already diagnosed and fixed once in this exact file, left unfixed in three of the four places it also applies, with a regression test that made the fixed site look like the whole fix.

**Suggested fix:** tcell v2.13 ships `Screen.PutStrStyled(x, y, str, style)`, which walks by grapheme cluster, advances by true display width, and clips to screen bounds — replacing all four hand-rolled loops with it removes this bug, Finding 3's wide-rune bug, and a latent combining-mark bug in one move, and is the direction tcell's own docs steer callers in (`SetContent` is the lower-level primitive `Put`/`PutStrStyled` are meant to replace for text).

### Finding 3: The target render loop (and the domain's own width accounting) count runes, not display cells — wide and zero-width runes silently destroy characters and desync the hit box from what's drawn

**Status: Partially fixed (2026-09-12).** The render-loop half is fixed the same way as Finding 2: the hand-rolled `col++`-per-rune loop in `Render`'s target-draw was replaced with `tcell.Screen.PutStrStyled`, which advances by true grapheme-cluster width. Regression test `TestRenderWideRuneTagDoesNotDropCharacters`, verified against the pre-fix code to actually reproduce the documented `"[9 日本語]"` → `"[9 日語"` character loss before confirming it passes against the fix. **The domain-side half — `core/game/target.go`'s `NewTarget`/`move`/`isHitAt` all using `utf8.RuneCountInString`, causing the hit box to desync from the rendered width for wide-rune tags — is deliberately left open.** Fixing it correctly needs a real display-width computation (grapheme-cluster segmentation, East-Asian-Width lookup), and the only such implementation already in this dependency tree is `uniseg`, pulled in transitively by tcell. Importing it directly into `core/game` would put a third-party, rendering-adjacent library inside a domain package that today has zero non-`core` imports — an invariant this project has verified and re-verified as load-bearing across every prior review pass. That's a real architectural trade-off, not a mechanical fix, so it was put to the project owner rather than decided unilaterally: given the choice between leaving it as rune-count, hand-rolling a stdlib-only width approximation, or importing `uniseg` directly, the owner chose to **leave the domain side as rune-count** — the desync is not reachable via the current fixed glyph set (only via a future or user-controlled wide-rune process name), and preserving `core/game`'s zero-outward-import boundary outweighs closing a currently-latent gap. Accepted, won't-fix for now; revisit if a live report ever surfaces. `tcellui.go:72-78`'s `col++` advances one column per *rune* regardless of the rune's actual display width. tcell's own cell model doesn't make this assumption — `CellBuffer.Put` computes true width via grapheme-cluster segmentation (2 for East-Asian-wide runes, 0 for combining marks/control characters). Reproduced: a tag `"[9 日本語]"` renders as `[9 日語` — two runes' worth of content silently vanish, because the wide `日`/`語` runes each claim two columns while the loop only advances one. A combining-mark tag (`"caféX"`) drops the accent and leaves a stray blank column instead.

**Not purely cosmetic — the domain measures width the identical, identically wrong way.** `core/game.Target`'s `NewTarget` (spawn bounds), `move` (right-wall bounce), and `isHitAt` (hit detection) all use `utf8.RuneCountInString`, the same one-column-per-rune assumption. For a tag containing wide runes, `core/game` believes the tag is *N* cells wide while the terminal renders up to *2N* — so the tag can overflow past where the domain thinks the wall is, and the rightmost visible glyphs sit outside what `isHitAt` will register as a hit. Since process names (the source of a target's tag content) can legitimately contain any UTF-8 the filesystem allows, a CJK- or emoji-named binary — trivially self-inflicted with one `ln -s` — hits this today.

**Currently non-live for the shipped kill-animation glyph set:** the one non-ASCII glyph already in the codebase, `"💥"`, is confirmed to always be the *entire* tag content for that animation frame (no adjacent characters to misalign), and `TestRenderMultiByteLabelColumnLayout` passes even under `RUNEWIDTH_EASTASIAN=1` (tcell's ambiguous-width override) because `✦` U+2726 is Neutral, not Ambiguous, under Unicode's East Asian Width property. The exposure is entirely in future/user-controlled tag content, not the current fixed glyph table.

**Severity: Moderate.** No crash, no data loss — but silent character loss in what's drawn, and a real, traceable desync between "what the player can see" and "what the player can click," in a game whose entire interaction model is click-what-you-see. Both reviews independently identified the render-loop half of this; one review additionally traced the domain-side consequence, which is included here since it's what elevates this above a purely cosmetic finding.

**Suggested fix:** same as Finding 2 — `PutStrStyled`/`Put` fixes the rendering half in one move. Making the domain's width measurement (`utf8.RuneCountInString` in `core/game/target.go`) display-width-aware instead of rune-count-aware is a separate `core` change (tcell already pulls in `uniseg` transitively, so the dependency is already present) and belongs in the same conversation as Finding 1/#38's chrome-contract fix, not bundled into this adapter's fix.

### Finding 4 (new): `Cleanup()` panics with `close of nil channel` on a real `tcell.Screen` if `Init()` was never called or failed before its internal `quit` channel is allocated — invisible to this file's own test suite by construction

**Evidence:** `tcellui.go:47-52`:
```go
func (a *UI) Cleanup() {
    a.cleanupOnce.Do(func() {
        close(a.done)
        a.screen.Fini()   // unconditional, regardless of whether Init ever ran
    })
}
```
I independently verified tcell's own source (`$GOMODCACHE/github.com/gdamore/tcell/v2@v2.13.10/tscreen.go`) directly: the real screen's `quit` channel is a struct field, nil by default, allocated only inside `Init()` (`tscreen.go:232`, `t.quit = make(chan struct{})`), and `Fini()`'s underlying `finish()` closes it with no nil guard (`tscreen.go:373-376`, `close(t.quit); t.finalize()`). Calling `Fini()` on a `tcell.NewScreen()` that was never `Init()`'d does panic with `close of nil channel`, confirmed by execution against a real screen on this machine.

**Why the existing 92%-covered, 23-test suite cannot catch this:** every test uses `tcell.NewSimulationScreen()`, whose `Fini()` explicitly nil-guards (`simulation.go:153`, `if s.quit != nil { close(s.quit) }`) — I confirmed this directly too, by re-running the equivalent scenario against a `SimulationScreen` and finding it returns cleanly with no panic (this also settles a separate disagreement between the two reviews about `Render`/`Size` before `Init` on the simulation screen — see §7). The double under test in this suite structurally cannot exhibit the bug the shipping type has.

**Reachability today: not live.** `application/game.Service.runLoop` only calls `Cleanup` (deferred) after `Init()`'s error has already been checked (`service.go:91-94`), and `cmd/pidshooter/main.go` never calls `Cleanup` itself. But the port's own doc comment (`outbound/ui.go:59-61`) says only that `Cleanup` "releases what Init acquired… idempotent: calls after the first are no-ops" — it does not say `Init` must have succeeded first, and the most idiomatic Go a future maintainer would reach for (`if err := ui.Init(); err != nil { ui.Cleanup(); return err }`, or a `defer ui.Cleanup()` placed before the `Init()` call at the composition root) panics in production on a real terminal. This is directly relevant to the still-open `docs/code-review.md` #46 (moving `Init`/`Cleanup` ownership to the composition root) — that exact refactor is what would put `Cleanup` on a path where `Init` hasn't necessarily run.

**Severity: Moderate.** A latent panic in the one method whose entire job is restoring the user's terminal from raw mode — and a class of bug (test double diverges from the real implementation at exactly the seam being tested) that no amount of testing against the current double would surface.

**Suggested fix:** gate `screen.Fini()` on whether `Init()` actually completed, not just on once-ness — an `initialized bool` set at the end of a successful `Init()`, checked inside the same `cleanupOnce.Do`. `close(a.done)` can stay unconditional (`a.done` is allocated in `NewUI`, never nil). Add a regression test for `Cleanup()` before `Init()` against a real `tcell.Screen` (not just the simulation one) — or explicitly document why that's out of reach for a unit test and rely on the guard alone. This should land before #46, not after.

### Finding 5 (reassessment of `docs/fable-review.md` S3 / `docs/security-issues.md` SEC-09, still OPEN): mouse-drag fires a kill on every motion sample — both reviews independently pinned the same root cause, one level deeper than previously documented, and independently converged on the same fix

**Evidence, confirmed live by both reviews via `tcell.SimulationScreen.InjectMouse`:** a single click-and-drag gesture (button held across several coordinates) produces one `ClickEvent` per motion sample, not one per gesture — `poll()` (`tcellui.go:163-168`) forwards every `*tcell.EventMouse` where `Buttons() == Button1`, with no deduplication by coordinate, time, or press/release transition.

**Root cause, pinned by both reviews independently at the same place:** `Init()` calls `a.screen.EnableMouse()` with no flags (`tcellui.go:38`). Both reviews read tcell's `EnableMouse` source directly and found that zero flags defaults to `MouseMotionEvents | MouseDragEvents | MouseButtonEvents` — XTerm's widest tracking mode (`\x1b[?1003h`), which reports continuous motion samples, not just press/release. Prior docs (`fable-review.md` S3, `security-issues.md` SEC-09) described only the symptom (`poll` forwards every `Button1` event); neither traced it to the terminal being told to emit motion samples at all.

**Traced downstream through real caller code by both reviews, independently, to the same conclusion:** in default (non-confirm) mode, `core/game.Confirmation.Request` returns the target directly with no gate; `drainEventQueue` (`application/game/service.go:169-181`) spawns a fresh `go s.killOrReap(...)` goroutine per event with no per-target dedup, and the target stays `Alive` — and therefore independently re-hittable — until the async kill result lands on a later frame tick. So N motion samples from one drag become N concurrent `ps`-subprocess-plus-`SIGKILL` goroutines against the same PID. (Redundant *late* signals don't double-award score credit — `applyKillSignals`' `sig.target.Kill()` case is guarded by `isAlive()` — but each still costs a wasted subprocess round-trip and syscall.)

**Status: confirmed still OPEN**, unchanged from `security-issues.md`'s listed status.

**Severity reassessment:** prior docs rated this Low. Both independent reviews, without prompting from each other, treated it as Moderate in this pass (one placed it under its "Moderate findings" section outright; the other argued explicitly for re-rating it, on the grounds that the amplified action is an irreversible `SIGKILL` of arbitrary in-scope processes, the amplification factor is unbounded in gesture length, the trigger is an entirely ordinary accidental mouse movement rather than anything adversarial, and the fix is a single function argument). This document adopts **Moderate**, on the same reasoning, with the caveat that `--confirm` mode already fully immunizes this (a pending confirmation blocks further clicks via `core/game.Input.OnClickAt`'s early return), so the exposure is scoped to the default mode.

**Suggested fix — both reviews converged on the identical, cheaper-than-previously-documented fix:** change line 38 to `a.screen.EnableMouse(tcell.MouseButtonEvents)`. This selects XTerm's basic click-tracking mode (`\x1b[?1000h`, press/release only) so the *terminal itself* never generates the intermediate motion samples — no state-tracking or deduplication logic needed in `poll()` at all (the previously-suggested "track previous button state and emit only on the press transition" fix is unnecessary once the terminal is told to stop over-reporting), and it reduces raw event volume system-wide as a side effect. One review flagged this as a wire-protocol claim verified against tcell's own source/simulation model but not against a real terminal's XTerm compliance — worth a quick real-tty smoke test before relying on it, though the library-level mechanism itself is unambiguous.

### Finding 6 (reassessment of `docs/fable-review.md` S4 / `docs/security-issues.md` SEC-10, still OPEN, adjacent to this file): unbounded concurrent kill goroutines, directly amplified by Finding 5

`application/game/service.go:175` (`go s.killOrReap(target, killSignals, done)`) spawns one goroutine per accepted `ClickEvent` with no cap and no per-PID dedup in `application/process/service.go`'s `Kill`. This lives outside `tcellui.go` and is unchanged in substance from the prior write-up, but it's the direct, currently-unmitigated consumer of Finding 5's amplification — N duplicate `ClickEvent`s from one drag become N concurrent `ps`-subprocess-plus-signal goroutines against the same PID, even though (per Finding 5) the *scoring* consequence of the duplicates is bounded by `isAlive()`. **Status: confirmed still OPEN.** Fixing Finding 5 at the `EnableMouse` level substantially neutralizes this in practice (no more duplicate events to amplify), though the underlying lack of a cap remains an independently-open gap in a different file.

## 7. Where the two independent reviews disagreed, and how it was resolved

1. **Whether `Render()`/`Size()` called before `Init()` panics on `tcell.SimulationScreen`.** One review reported a reproduced nil-pointer panic inside tcell's `drawCell`; the other reported both calls return cleanly (`Size()` → `(0,0)`, `Render()` → no-op). This was a directly, cheaply re-testable empirical claim, so it was re-run independently on this machine rather than adjudicated by argument: three scratch tests (`Render` before `Init`, `Size` before `Init`, `Render` after `Cleanup`) all returned cleanly with no panic, against `tcell v2.13.10` on Go 1.26.5/darwin-arm64. **This reproduced the "returns cleanly" result, not the panic.** The panic claim did not hold up on re-test and is treated as refuted for this document; the real, verified issue in this area is the narrower one in Finding 4 (a real, non-simulated screen's `Fini()` panicking specifically when `Init()` was never reached far enough to allocate its `quit` channel — a different code path than the one that was re-tested here and found safe).

2. **Severity/consequence of the row-0 HUD-overdraw finding (Finding 1).** One review rated it cosmetic-only, reasoning that hit-detection is independent of what's rendered. The other traced the actual click path and concluded the invisible target remains fully killable. This was resolved by direct code reading rather than re-running either review's repro: `core/game.Roster.hitAt` (`roster.go:49-53`) and `Target.isHitAt` (`target.go:98-104`) have no row-based exclusion of any kind — they test only `State == Alive` and the tag's rectangle. The trace holds up exactly as the second review described it. **Resolved in favor of the more severe characterization**, and this document rates Finding 1 accordingly — the first review's underlying observation (hit-detection doesn't read the rendered buffer) was correct as stated, it just stopped one inferential step short of the actual consequence.

3. **Severity of the drag-to-kill finding relative to the prior single-file docs' Low rating.** Not a disagreement *between* the two reviews — both independently reassessed it upward to Moderate without being asked to reconsider severity, which this document treats as a stronger signal than either alone and adopts (Finding 5).

## 8. Platform applicability

Both reviews and this reconciliation were produced entirely on macOS (Darwin 25.6.0, arm64). Unlike `docs/osprocess-findings.md`'s subject, `tcellui.go` itself contains **zero `runtime.GOOS` branches** — every platform dependency is inside tcell, not this file. Both reviews independently cited tcell source files to support cross-platform claims:

- Finding 4's mechanism (`t.quit` allocated in `Init`, closed unguarded in `finish`) lives in `tscreen.go`, shared across every tty platform tcell supports — not in a `tty_unix.go`/`tty_windows.go` platform file.
- Finding 5's mechanism (`EnableMouse`'s zero-flag default, and the XTerm `?1002h`/`?1003h` escape sequences it emits) is in the same shared `tscreen.go`, gated only on the terminal's own `mouse` terminfo capability, not on the host OS.
- Minor #11's mechanism (`x/term.MakeRaw` clearing `ISIG`) is in `term_unix.go`, shared by Linux and Darwin (only `term_windows.go`/`term_plan9.go` differ).

Findings 1, 2, 3, and every Minor/Low finding are pure Go-level logic over `outbound` types and stdlib `unicode`/`fmt`/`strings` — none of their evidence touches a Darwin-only code path. No live Linux execution pass was performed for this document; given the near-total absence of platform branching in the subject file itself (in contrast to `osprocess.go`, where a live Linux+macOS pass actually changed several findings' conclusions), the marginal value of one is low. The one item worth a cheap real-hardware check before fully trusting it is Finding 5's specific escape-sequence claim (`EnableMouse(tcell.MouseButtonEvents)` behaving as expected against a real terminal emulator, not just tcell's own simulation/source-level model) — both reviews flagged this same caveat independently.
